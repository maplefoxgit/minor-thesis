# Reproducibility

## Goal

These steps let a supervisor clone the repository and reproduce the complete bounded evidence pack on a local machine.

## Prerequisites

- Python 3.11 or newer
- `make`
- a local shell environment

No external networked runtime, Kubernetes environment, Docker environment, or O-RAN control-plane deployment is required.

The checked-in final release manifest is a retained record and is not regenerated by the commands below. Before rerunning the workflow, verify that the checkout is at the intended release tag and preserve or inspect `results/reports/final_release_manifest.json`. Reproduction commands overwrite generated reports. Exact timing values and result-file hashes can differ on another host or software environment.

## Fresh Reproduction Steps

1. Clone the repository and enter it.

```bash
git clone <repository-url>
cd minor-thesis
```

2. Create the local environment and install dependencies.

```bash
make install
source .venv/bin/activate
```

3. Run validation, compilation, verification, tests, and experiments E1 to E7.

```bash
make run-all
```

4. Reproduce the retained repeated E5 distribution.

```bash
python experiments/run_e5_repeated.py --warmups 5 --trials 30
```

5. Reproduce the E6-P pure-verification performance characterisation for the three E6 conditions.

```bash
python experiments/run_e6_repeated_performance.py --warmups 5 --trials 30 --iterations 500
```

6. Reproduce the bounded S1 verifier-only scale study.

```bash
python experiments/run_s1_multislice_verifier_scaling.py --slices 2 3 4 10 --warmups 5 --trials 30 --rss-trials 5
```

7. Inspect the generated evidence.

```bash
ls policies/generated
ls results/reports
ls results/metrics
```

## What A Successful Reproduction Looks Like

- `make run-all` exits successfully.
- `pytest` reports 69 passing tests.
- `results/reports/verification_report.json` reports `overall_status: "pass"` for the bounded baseline.
- `results/reports/experiment_summary.json` reports seven passing experiment groups and zero failures.
- E6 reports the compiled-policy condition as the only tested condition satisfying required reachability, forbidden-path blocking, and the terminal-service constraint simultaneously.
- E7 reports that the clean baseline verifies, a byte-only policy mutation is rejected before graph construction, and clean regeneration restores a passing bundle.
- `policies/generated/` contains exactly three `*.generated.*` policy artefacts and one manifest.

The separate performance and scale characterisation runs succeed when:

- repeated E5 reports 30 measured runs after five warm-up runs,
- E6-P reports 30 measured batches after five warm-up batches for each of the three E6 conditions,
- S1 completes the 2, 3, 4, and 10-slice generated graph cases and detects the injected forbidden route at every tested size.

These three studies characterise local cost or scale. They do not extend the functional or security claim.

## Retained Final Capture

The retained `sit746-evidence-2026-09-02` release was captured on macOS 26.6.2 on an Arm-based host using CPython 3.12.13 and 10 logical processors. The release manifest records source commit `0cd37db614413f773faceb593e08bdb456b70e95`. The retained release tag points to commit `e51e66aef8fdc2381f0793d9ab14c8049efbfee8`.

For E5, five warm-up runs preceded 30 measured runs. The median instrumented harness time was 165.683937 milliseconds. The median sum of the six separately measured pipeline stages was 28.621479 milliseconds. The largest median per-stage Python allocation was 82,853 bytes. The harness time also includes orchestration, temporary-directory work, separate allocation profiling, metric aggregation, and result writing. The allocation value comes from Python `tracemalloc`; it is not whole-process memory.

For E6-P, five warm-up batches preceded 30 measured batches for each condition, with 500 verifications in each batch. Median pure-verification time was 0.023750 milliseconds for the permissive graph, 0.006054 milliseconds for deny-all, and 0.012360 milliseconds for the compiled-policy graph. These timings characterise execution cost only. The separate E6 functional comparison establishes that the compiled-policy condition is the only condition satisfying all functional criteria.

For S1, five warm-up runs preceded 30 measured runs at each generated graph size, with five isolated resident-memory workers per size. The tested cases represented 2, 3, 4, and 10 slices. Median verification time rose from 0.0150415 milliseconds at 2 slices to 0.2779585 milliseconds at 10 slices. The condition medians for worker peak process resident memory ranged from 32.4375 to 32.609375 mebibytes. The injected forbidden route was detected at every tested size.

## Interpretation Boundary

Successful reproduction shows only that the bounded local proof of concept behaves as designed in the repository's static model.

- E5 describes one host and one fixed workload. It does not establish production performance or cross-platform repeatability.
- E6-P measures only the local pure-verification step. It is not functional or security evidence, a security-effectiveness score, or a benchmark against another system.
- E7 checks the bytes of three manifest-listed generated policy files before graph construction. It does not provide manifest authentication, detection of coordinated policy and manifest tampering, protection against a change after the check, topology, query, or report binding, detection of a compromised compiler or verifier, or runtime drift observation.
- S1 uses generated in-memory graphs directly at the verifier layer. It bypasses the end-to-end intent schema, semantic validator, compiler, compiled-policy loader, and topology-to-policy graph builder.
- No capacity breaking point is claimed because no time or memory threshold was declared before the S1 run.

The repository does not demonstrate runtime enforcement, live O-RAN security, production deployment readiness, complete operational assurance, or production scalability.
